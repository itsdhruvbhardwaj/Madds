# Rewarded-ad credits in Workspace

App settings > Rewarded-ad credits controls the Madds credits earned for one completed, server-verified rewarded ad. Enter 1–100,000 whole credits and Save ad reward. Zero is not a valid offer; use the existing rewarded-ad placement switch to disable ads. Existing balances, welcome credits, placements, purchases and AdMob verification metadata are unchanged.

The protected /api/admin/settings/rewarded-credits GET/PATCH endpoints require a verified, allowlisted administrator. Edits include expectedRevision, fail on stale writes/first-save races, and record last-editor name and time. Credits are stored in a separate RewardedCreditSettings document so saving other settings cannot overwrite the reward. No override is created during deployment: the current REWARDED_AD_CREDITS environment value remains in effect until the first explicit Workspace save.

The public /api/rewarded-ads/config and authenticated /api/rewarded-ads/attempts read the current amount without caching. Each new attempt snapshots its promised rewardCredits. Verified SSV callbacks continue to redeem that snapshot transactionally; duplicate grants stay protected. A later Workspace edit cannot reduce or increase the reward for an already-created attempt. Legacy attempts missing rewardCredits retain the existing environment fallback. The original AdMob unit, item and amount verification settings must remain valid and unchanged.

A settings read failure disables new offers/attempts instead of substituting a guessed amount. Verification of already-started ads does not read the new settings document. The existing Android build already refreshes reward offers and compares the displayed amount with the new attempt's amount before showing an ad; if different, it asks the user to tap again after displaying the new reward. No Android code change or AdMob console change is needed for this feature. Deploy backend first, then Studio; later amount changes need no redeployment or restart.
